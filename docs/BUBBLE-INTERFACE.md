# Yazhi Bubble Interface (YBI)

**Status:** Phase 0 shipped: component system, Foundry overview and project pages.
**Code:** `src/bubble/` (components), `src/lib/yazhi-api/` (transport), `src/lib/foundry/` (first product), `src/app/foundry/` (routes).
**Developer guide (API, calculations, recipes):** [YBI-DEV-GUIDE.md](./YBI-DEV-GUIDE.md).
**Related:** `docs/DESIGN-SYSTEM.md` (thinai palette), `NEXT_ACTION.md` (Oct Pilot / Dec Launch), yazhi-api `services/yazhi/proto/insight.proto`, yazhi-api `docs/factory/architecture.md`.

## 1. Why

Yazhi Dev began as a marketing site: 3D world, scroll set pieces, hand-built sections. The Pilot and Launch scopes are product surfaces: Foundry, API keys, playground, skills registry and ecosystem directory. All of them are views over yazhi-api data. Hand-building each one the way the marketing sections were built would be slow, would drift visually, and could not keep pace with yazhi-api's service count.

YBI aims to make a new yazhi-api-backed page take **one RPC call and one view function**, rendered with components that already look like Yazhi.

## 2. The idea in one picture

```
yazhi-api (gRPC :50051)
   │  Connect / gRPC-JSON gateway
   ▼
src/lib/yazhi-api/rpc.ts        unary(service, method, req)  ← one transport, server-only
   ▼
src/lib/<product>/client.ts     load*() → { data, source: live | sample }
   ▼
src/lib/<product>/views.ts      view(data, source) → Block[]  ← pure, JSON-serialisable
   ▼
src/app/<route>/page.tsx        <BubbleView blocks={…} />      ← 3 lines
   ▼
src/bubble/                     tone → core → patterns → spec, inside BubbleShell
```

A page is **data describing blocks** (`Block[]`). The blocks themselves are data too. Views can therefore be:

1. written by a developer as a pure function (today),
2. generated by a scaffolder (Phase 2),
3. emitted by an agent such as Adhan and validated against the Block schema (Phase 3),
4. served directly by yazhi-api (Phase 3, optional).

The renderer does not care which of these produced the blocks.

## 3. Scope: what YBI is and is not

**In scope**
- Product and tool surfaces backed by yazhi-api: Foundry, keys, playground, registry, status, and operator views that are safe to expose publicly.
- Data display (stats, meters, stage tracks, findings, tables, key/value), navigation (shell, breadcrumbs), empty and notice states.
- Bilingual copy (Tamil/English) through the site's TAM · ENG · BOTH toggle.

**Out of scope**
- Marketing sections, the 3D thinai world, scroll set pieces. They stay in `src/components/{hero,sections,footer}`.
- Form-heavy flows, until Phase 2 adds form blocks; `/onboarding` stays as-is.
- Anything that mints credentials or reads raw audit rows. That remains the loopback-only yazhi-api console (`console/`, `docs/CONSOLE.md`).

## 4. Structure

```

├── patterns/           compositions of primitives
│   ├── PageHeader      crumbs, eyebrow, bilingual title, pills
│   ├── BubbleCard      entity card: title + meter + pills + facts
│   ├── StageTrack      pipeline stages: done | active | attention | pending | skipped
│   ├── FindingList     insight Finding[], worst first
│   ├── KeyValue · DataTable · EmptyState (with Yazh) · Notice

│   ├── BubbleShell     app frame: mark, product, section nav, language toggle
│   └── ShellNav        the only client component (needs pathname)
└── spec/

    └── BubbleView.tsx  Block[] → components (exhaustive switch)

src/styles/bubble.css   .ybi-bubble surface, dot, stage link (zero JS)
src/lib/yazhi-api/rpc.ts        server-only Connect-JSON unary client
src/lib/foundry/{types,projects,sample,client,views}.ts
src/app/foundry/{layout,page}.tsx, [project]/page.tsx
```

### Rules

1. **Layer direction:** `tone ← core ← patterns ← spec`, and `shell` builds on `core`. `src/bubble` never imports from `src/lib/*`. Product code imports YBI; YBI never imports product code.
2. **Server-first:** primitives are Server Components styled by CSS. A client island is added only when a block needs interaction (search box, pagination, copy button), and it is added as a pattern, not inside a primitive.
3. **Tones, not colours:** components accept a `Tone`. Semantic tones map onto thinai hues (ok → mullai, warn → marutham, error → palai, info → neytal), so status colour stays inside the brand palette. No state is shown by colour alone; every one has a text label.
4. **Honest data:** every data page renders a `notice` block saying whether its numbers are *live* or *sample*, with the source. Missing data renders as "—" or an empty state, never as zero or a made-up value.
5. **Bilingual by type:** user-facing headings are `BiText`. Letter-spacing is reset on `[lang="ta"]` inside tracked labels, because tracking breaks Tamil glyph clusters apart.
6. **One transport:** all yazhi-api reads go through `unary()`. It runs on the server only, and the API key never reaches the browser.

## 5. Scaling with yazhi-api

yazhi-api is gRPC-first (`services/server.py`) with bearer-token metadata (`services/interceptors.py`). YBI talks to it with the **Connect protocol's JSON mapping**, `POST {YAZHI_RPC_URL}/{package.Service}/{Method}`. Any gRPC-JSON gateway can serve that without changes to yazhi-api (Envoy `grpc_json_transcoder`, `connect-python`, or either behind the existing Cloudflare Tunnel).

Each new yazhi-api service adds:

| Step | File | Size |
|---|---|---|
| Message types (proto3 JSON: camelCase, int64 as string) | `src/lib/<svc>/types.ts` | mirror of the `.proto`; codegen from Phase 2 |
| Loader with live → sample fallback | `src/lib/<svc>/client.ts` | ~30 lines |
| View function(s) | `src/lib/<svc>/views.ts` | pure `data → Block[]` |
| Route | `src/app/<route>/page.tsx` | ~5 lines |

### Page ↔ RPC map

| Page | RPC | Status |
|---|---|---|
| `/foundry` | `yazhi.insight.v1.YazhiInsight/GetQualityOverview` | ✅ Phase 0 |
| `/foundry/[project]` | `YazhiInsight/GetDomainQuality`, `GetPipelineHealth` | ✅ Phase 0 |
| `/foundry/[project]/records` | `YazhiInsight/ListRecords`, `GetRecord` | Phase 1 |
| `/foundry/findings` | `YazhiInsight/ListFindings` | Phase 1 |
| site-wide status bubble | `yazhi.v1.YazhiSystem/GetHealth` (unauthenticated) | Phase 1 |
| `/foundry` pipeline list (live) | **proposed** `yazhi.factory.v1.YazhiFactory/ListPipelines` | Phase 2 (needs yazhi-api) |
| `/keys` | `YazhiApiKeys` + Circle auth (`docs/PRD-DEVELOPER-COMMUNITY.md`) | Phase 2 |
| `/playground` | chat/query services + agent-emitted blocks | Phase 3 |
| `/registry` | yazhi-skills catalog | Phase 3 |

### What a Foundry project is

A Foundry project is **one yazhi-api domain's data programme**, one per `core/router.DOMAIN_MODEL` entry: `legal`, `education`, `governance`, `health`, `sovereign`, `core`. Each project has:

- its YazhiFactory pipelines (`factory/configs/<domain>/<language>/*.json`),
- its stage CLI, if it has one (legal: fetch → parse → validate → embed),
- the shared factory loop (collect → audit → raw → enrich),
- its corpus and quality as reported by YazhiInsight.

`src/lib/foundry/projects.ts` mirrors the factory catalog as a snapshot, because no RPC lists it yet. That gap is the first yazhi-api ask below.

## 6. Adding things

**A page:** write `load()` in `src/lib/<x>/client.ts`, write `view()` in `views.ts`, then `export default async function Page() { … return <BubbleView blocks={view(data, source)} /> }`. Wrap sibling routes in a `layout.tsx` with `<BubbleShell>`.

**A block kind:** add the component under `patterns/`. Add `{ kind: "…" } & Props` to the `Block` union in `spec/types.ts`, then add the case to `BubbleView`. The `never` check fails the build until you do. Export it from `index.ts`.

**A primitive:** only if no pattern can compose it from `Bubble` + `Pill` + `Meter` + `Stat`. The primitive layer is meant to stay small.

## 8. Open questions

1. **Key for Insight.** `YazhiInsight` requires an API key, and `api_keys.domain` cannot issue `core` or `governance` keys yet (yazhi-api `CONTEXT.md`). Which domain/role should yazhi-dev's read-only key use? `sovereign.user` is the likely stopgap.
2. **Gateway.** Envoy transcoder or `connect-python`? Envoy needs no Python changes. `connect-python` keeps everything in one process, which fits the local-first constraint.
3. **Public vs operator.** Insight exposes record text and credential statistics. Should `/foundry` be public, cohort-only (FDE Foundry interns), or split into public quality and gated records? Phase 1 needs an answer before records go live.
